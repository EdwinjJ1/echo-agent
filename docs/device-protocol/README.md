# 回声设备协议 v1

> 状态：草案（2026-10）。标着「v1 已实现」的部分，回声的 Mac 版已经支持，Windows 版正在移植；标着「草案」的部分是定下来的方向，还会改。
> 许可：Apache-2.0。
> English: [README.en.md](README.en.md)

回声（echo agent）是电脑上的语音 AI agent：按住说话，它把活派给你电脑上的 Claude Code、Codex、opencode 等编程 Agent，
要批准的一步、做完的结果都回到你面前。这份协议让别的硬件也能当回声的入口：桌上的一颗按键、一盏状态灯、夹在衣领或眼镜腿上的小麦克风、手表。

设备不跑 agent，也不认字。它只做三件事：**把人的话送进来**（按键、麦克风、唤醒词），**把状态带出去**（灯、屏幕、喇叭），**替人按一下**（批准）。
认字、派活、和 Agent 打交道都在电脑上的回声里做。下文把跑着回声的那台电脑叫**主机**。

## 1. 能力分级

设备在 `hello` 里列出自己有什么（[第 4 节](#4-握手hello)），主机按它决定发什么、怎么解释按键。下面几级是常见的组合，不是硬性档位：

| 级别 | 有什么 | 能做什么 | 例子 |
|---|---|---|---|
| L0 状态灯 | 灯，可以再加一颗键 | 看几个在干活、有没有等你批准；按一下批准 | 显示器边上的一颗灯 |
| L1 按住说话 | L0 + 麦克风 | 按住说话、松开发出 | 桌面派活键（第一个原型） |
| L2 能说话 | L1 + 喇叭 | 听回声念回答的那一句 | 带喇叭的桌面款 |
| L3 有屏幕 | + 屏幕 | 看要批的是什么、最近一条结果、听出的字 | 手表、带屏的桌面款 |
| L4 能看 | + 摄像头 | 拍一张给回声看 | 眼镜 |

另外两样和级别无关：**唤醒词**（设备自己听「回声回声」「echo echo」，听到之前声音不出设备）和**电池**。

主机必须能对付只有一部分能力的设备：没有麦克风的不送语音事件，没有屏幕的不送批准详情。设备不认识的字段和事件一律不理。

## 2. 传输方式

同一套消息（[第 3 节](#3-消息格式)）走四条路，区别只在怎么连、要不要加密：

| 方式 | 适合 | 配对和加密 | 状态 |
|---|---|---|---|
| USB 直连 | 桌面款，插在电脑上 | 不配对、不加密：插上就是信任，和 USB 键盘、麦克风一样 | v1 已实现：Mac 已支持，Windows 移植中 |
| 局域网直连 | 桌面款，Wi-Fi，和电脑在同一个网里 | 每台设备一把密钥，ChaCha20-Poly1305 | 草案 |
| 经中继 | 不在同一个网里 | 同上，中继只转密文 | 草案 |
| 经手机蓝牙 | 穿戴款（领夹、眼镜） | 同上，手机只转密文 | 草案 |

一台设备可以同时有几条路（例如插着 USB 又连着 Wi-Fi），主机按设备 `id` 认出是同一台，回复走请求来的那条路，状态事件走它最近用过的那条。

## 3. 消息格式

消息都是 UTF-8 的 JSON 对象。三种，和回声手机遥控的应用层一样：

```jsonc
{"id": "7", "m": "hello", "p": {...}}                          // 请求：m 是方法，p 是参数（可省略）
{"id": "7", "ok": true, "r": {...}}                            // 成功的回复，id 和请求一样
{"id": "7", "ok": false, "e": {"code": "usage", "message": "…"}}  // 失败的回复
{"ev": "status", "d": {...}}                                   // 事件：没有回复
```

- 请求两个方向都可以发（设备发 `hello`，主机发 `provision`），`id` 由发的一方定，是不超过 36 个字符的字符串，在一条连接上不重复就行（递增的数字也可以）。
- 收到的请求不认识，回 `{"ok":false,"e":{"code":"unknown_method"}}`；事件不认识就丢掉。
- 错误码：`usage`（参数不对）、`not_found`、`busy`、`unavailable`（这台主机做不了，`message` 写原因）、`unknown_method`、`version`（协议版本不支持）。
- 时间：`t`、`at` 这类字段都是毫秒整数。`t` 是设备自己的单调时钟（开机以来的毫秒数就行），只用来算两个事件之间隔了多久；`at` 是 Unix 毫秒时间。
- 大小：一条消息不超过 64 KiB；除了 `voice.chunk`，都应该在 4 KiB 以内。

## 4. 握手：hello

连上之后设备先发 `hello`，主机回过之后才算连好。主机也可以发 `sync` 事件（`{"ev":"sync"}`）请设备重发一次 `hello`，设备收到必须照做。

```jsonc
// 设备 → 主机
{"id": "1", "m": "hello", "p": {
  "v": 1,
  "device": {
    "id": "ab12cd34ef56",          // 这台设备的固定标识：自己生成一次存起来，或配对时主机分配的（第 9 节）
    "model": "echo-desk-s3",       // 型号，厂商自己起
    "name": "桌面派活键",           // 给人看的名字，可省略
    "fw": "0.1.0",                 // 固件版本
    "maker": "echo-reference"      // 谁做的，可省略
  },
  "caps": {                        // 有什么，没有的就不写
    "button": {"count": 1},
    "light": {"kind": "rgb", "count": 1},        // kind：mono（单色）| rgb | ring（灯环，count 颗）
    "mic": {"via": "uac", "rates": [16000]},     // 见第 6 节
    "speaker": {"via": "stream", "codecs": ["opus"]},
    "screen": {"w": 240, "h": 240},
    "camera": {"formats": ["jpeg"]},
    "wake": {"phrases": ["回声回声", "echo echo"]},
    "battery": true
  }
}}

// 主机 → 设备
{"id": "1", "ok": true, "r": {
  "v": 1,                                        // 主机用哪个版本说话
  "host": {"name": "Alex 的 MacBook Pro", "app": "echo agent", "version": "0.1.83"},
  "mic": {"via": "stream", "codec": "opus", "rate": 16000},   // 主机挑的录音方式，没有麦克风时没有这一项
  "now": 1761650000000,                          // 主机现在的 Unix 毫秒时间
  "features": ["status", "approve", "voice"]     // 这台主机会的东西，见下表
}}
```

`features` 里可能有：

| 值 | 意思 |
|---|---|
| `status` | 会发 `status` 事件（第 7 节） |
| `approve` | 设备上按一下能批准；`approve` 请求可用 |
| `voice` | 按住说话可用（第 6 节） |
| `approvals` | 会给有屏幕的设备发 `approvals` 事件 |
| `transcript` | 会给有屏幕的设备发 `transcript` 事件 |

握手之后主机马上发一次 `status`，设备据此点灯。

## 5. 按键

按键只报按下和松开，什么意思由主机按当时的状态定。这样只有一颗键的设备也不用自己记状态，各家设备用起来一样。

```jsonc
{"ev": "button", "d": {"action": "down", "t": 81234}}
{"ev": "button", "d": {"action": "up", "t": 81990}}
// 有几颗键时带 "id"：从 0 开始的编号，0 是主键；只有一颗时可以不带
```

主机怎么解释（一颗键时）：

- **按住说话**：按下就开始听（声音来自设备的麦克风；设备没有麦克风时用电脑的），按住超过 **400 毫秒**算说话，松开就把这句话交给回声，和电脑上按快捷键说话是同一条路。
- **轻按一下**（按下到松开不到 400 毫秒）：灯在「等你批准」时，批准最早的那一个请求；不然只把「做完了 / 没做完」的灯收掉。这一下录到的声音丢掉。
- 拒绝、回答选择题：按住说出来（「不行」「选第二个」），回声听得懂。选择题不能靠按一下回答。
- 400 毫秒按 `t` 算（设备时钟），不按事件到达主机的时间算：经中继时两条消息之间的延迟会差很多。

## 6. 声音

### 6.1 麦克风

设备在 `caps.mic.via` 里说声音怎么来：

| `via` | 声音怎么到主机 | 用在 |
|---|---|---|
| `uac` | 设备同时是一个 USB 麦克风（USB Audio Class），主机按住说话时从这个输入录音 | USB 直连 |
| `stream` | 设备自己录，用 `voice.*` 消息一段段送过来 | 所有方式（USB 上也可以） |

`stream` 时设备还写 `codecs`（`pcm16`、`opus`）和 `rates`，主机在 `hello` 的回复里挑一种。

按住说话时设备这样发（`stream`）：

```jsonc
{"ev": "button", "d": {"action": "down", "t": 81234}}
{"id": "9", "m": "voice.begin", "p": {"sid": "s1", "codec": "opus", "rate": 16000}}   // 回 {"sid":"s1"}
{"ev": "voice.chunk", "d": {"sid": "s1", "n": 1, "data": "<base64>"}}                  // 约 200 毫秒一段
{"ev": "voice.chunk", "d": {"sid": "s1", "n": 2, "data": "<base64>"}}
{"ev": "button", "d": {"action": "up", "t": 81990}}
{"id": "10", "m": "voice.end", "p": {"sid": "s1"}}                                     // 回 {"text":"帮我看看 CI 为什么挂了"}
```

- 按下就开始录、开始发，不等主机回话：经中继时一个来回要半秒多，等的话第一个字就没了。轻按一下的那一小段由主机丢掉。
- `voice.chunk` 是事件，没有回复；`n` 从 1 起，一句话里递增，主机丢掉重复的和更早的。
- `voice.end` 的回复是听出的字；这一下是轻按（被当成批准）时回 `{"text":"","discarded":true}`。
- 主机要等 `button up` 和 `voice.end` 都到了才把话交出去。
- 一句话最长 3 分钟，超过的部分主机不要。

**编码**：

| `codec` | `data` 里是什么 | 码率 |
|---|---|---|
| `pcm16` | 16 位小端单声道 PCM，采样率 `rate` | 16 kHz 时 256 kbps（base64 后约 340 kbps） |
| `opus` | 一串 Opus 包，每个前面两个字节（大端）写它的长度；单声道，`rate` 取 16000，每包 20 毫秒 | 16–24 kbps |

USB 和局域网上 `pcm16` 就够了；经中继、经蓝牙一定要用 `opus`。主机都应该能解这两种。

### 6.2 喇叭（草案）

回声只念回答最前面给耳朵听的那一两句。主机给有喇叭的设备发：

```jsonc
{"ev": "say", "d": {"text": "CI 挂在 lint 上，我已经让 Codex 去修了。"}}            // 有屏幕的设备可以显示
{"ev": "audio", "d": {"id": "a1", "codec": "opus", "rate": 16000, "n": 1, "data": "<base64>", "last": false}}
```

`caps.speaker.via` 为 `uac` 时主机直接把声音放到这个 USB 输出上，不发 `audio`。主机念不了（比如这个账号没有云端的声音）时什么都不发，设备不要自己合成。

## 7. 状态和批准

### 7.1 status（v1 已实现）

主机在状态变了的时候发，没变也至少每 30 秒发一次（同时当心跳）：

```jsonc
{"ev": "status", "d": {
  "seq": 42,                  // 一次握手之内递增，设备只认更大的；重新握手后从 1 算起
  "light": "waiting",         // 灯该是什么样，见下表
  "working": 2,               // 正在干活的：后台任务 + 回声自己在答的
  "waiting": 1,               // 等你处理的请求（批准一步、回答选择题）
  "latest": {                 // 最近结束的一个任务，没有时为 null
    "agent": "Codex",
    "status": "done",         // done | failed
    "title": "修好了登录页的跳转",   // 一行字，最多 60 个字符
    "at": 1761650000000
  }
}}
```

`light` 由主机定好，只有一颗灯的设备照着亮就行，不用自己算优先级。主机按这个顺序取第一个成立的：

| `light` | 什么时候 | 建议的样子（RGB / 单色） |
|---|---|---|
| `listening` | 主机正在听这台设备说话 | 白色常亮 / 常亮 |
| `waiting` | 有请求等你处理 | 琥珀色闪 / 快闪 |
| `failed` | 最近一个任务没做完，还没被看过 | 红色常亮 / 三下一组地闪 |
| `working` | 有任务在干活，或回声正在答 | 蓝色呼吸 / 慢呼吸 |
| `done` | 最近一个任务做完了，还没被看过 | 绿色常亮 / 亮 2 秒灭 2 秒 |
| `idle` | 都没有 | 灭，或很暗 |

`failed`、`done` 在任务结束 10 分钟后、或人在设备上按过一下之后变回别的样子。主机断开（USB 拔了、连接断了，或 75 秒没收到 `status`）时设备自己显示「没连上」（建议：红色很暗地慢闪），这个状态不由主机发。

### 7.2 approve（v1 已实现）

有屏幕的设备可以自己挑批哪个、允许还是拒绝：

```jsonc
{"id": "12", "m": "approve", "p": {"id": "req-7", "allow": true}}   // 回 {"ok":true}
{"id": "13", "m": "approve", "p": {}}                               // 不带 id：批准最早的那个，和轻按一下一样
```

找不到、或者那是一道选择题，回 `not_found` / `usage`。

### 7.3 approvals、transcript（草案）

主机只给 `caps.screen` 的设备发：

```jsonc
{"ev": "approvals", "d": {"items": [
  {"id": "req-7", "agent": "Claude Code", "kind": "command", "title": "运行命令", "detail": "npm test"}
]}}
{"ev": "transcript", "d": {"text": "帮我看看 CI", "final": false}}
```

`kind`：`command`（跑命令）、`fileChange`（改文件）、`permissions`、`tool`、`question`（选择题，只能说着回答）。

## 8. USB 直连（v1 已实现）

第一个原型：ESP32-S3 插在电脑上，被认成一个 USB 麦克风加一个串口。不用 Wi-Fi、不配对、不加密。

**USB 描述符**

- 复合设备：CDC ACM（串口）一组接口，有麦克风时再加 USB Audio Class 的麦克风（UAC 1.0 或 2.0，16 位单声道，16 kHz 或 48 kHz）。
- CDC 的通信接口的接口字符串（`iInterface`）必须是 **`echo-device`**。主机只打开有这个接口名的 USB 设备的串口，别的串口一概不碰（不会去动别人的开发板、3D 打印机）。
- 设备序列号（`iSerialNumber`）每台不同。主机用它把串口和同一台设备的 USB 麦克风对上。
- VID/PID 由厂商自己定，主机不看。

**串口上的格式**

- 一行一条消息：UTF-8 JSON，`\n` 结尾，行内不能有换行。波特率等串口参数不起作用，主机设成 115200 8N1。
- 主机打开串口后要拉高 DTR：常见的 CDC 实现（TinyUSB 等）在 DTR 为低时当作没人在听，不往外发数据。
- 主机打开串口后发 `{"ev":"sync"}\n`，设备回 `hello`。设备在串口被打开（DTR 拉高）时也可以主动发 `hello`。1.5 秒内没有 `hello`，主机再发一次 `sync`，三次都没有就当它不是回声设备，直到下次插拔。
- 主机关串口（退出、睡眠）或拔线，设备就当主机断了。
- 麦克风 `via` 写 `uac` 时主机从 USB 麦克风录音，串口上只有按键和状态；写 `stream` 时 `voice.*` 也走串口（不能做 UAC 的板子、模拟设备用这个）。
- 不以 `{` 开头的行主机丢掉，固件可以把调试日志也打在这个串口上，但别太多。

**一次完整的交互**（`>` 主机发的，`<` 设备发的）：

```
> {"ev":"sync"}
< {"id":"1","m":"hello","p":{"v":1,"device":{"id":"3c84279a10b4","model":"echo-desk-s3","fw":"0.1.0"},"caps":{"button":{"count":1},"light":{"kind":"rgb","count":1},"mic":{"via":"uac","rates":[16000]}}}}
> {"id":"1","ok":true,"r":{"v":1,"host":{"name":"Alex 的 MacBook Pro","app":"echo agent","version":"0.1.83"},"mic":{"via":"uac","rate":16000},"now":1761650000000,"features":["status","approve","voice"]}}
> {"ev":"status","d":{"seq":1,"light":"idle","working":0,"waiting":0,"latest":null}}
< {"ev":"button","d":{"action":"down","t":120400}}
> {"ev":"status","d":{"seq":2,"light":"listening","working":0,"waiting":0,"latest":null}}
< {"ev":"button","d":{"action":"up","t":122950}}
> {"ev":"status","d":{"seq":3,"light":"working","working":1,"waiting":0,"latest":null}}
> {"ev":"status","d":{"seq":4,"light":"waiting","working":1,"waiting":1,"latest":null}}
< {"ev":"button","d":{"action":"down","t":151000}}
< {"ev":"button","d":{"action":"up","t":151180}}
> {"ev":"status","d":{"seq":5,"light":"working","working":1,"waiting":0,"latest":null}}
```

## 9. 配对和每台设备的密钥（草案）

走网络的设备（局域网、中继、蓝牙）要先配对。和手机不同，**每台设备一把自己的密钥**：

- 主机给设备生成设备标识 `deviceId`（16 字节随机）和设备密钥 `K`（32 字节随机），自己记在设备列表里。
- 设备被拆开、闪存被读出来，泄露的只是这一台的 `K`：别人能冒充这台设备，但看不到手机的通信、别的设备的通信，主机删掉这台设备后它就失效。
- 在主机上「移除」一台设备：删掉它的 `K`，告诉中继不再放它进来（[第 11 节](#11-经中继草案)）。重新配对手机不影响设备，反过来也一样。

设备存的配对信息：

```jsonc
{"v": 1, "device": "<deviceId>", "key": "<K>", "host": "Alex 的 MacBook Pro",
 "relay": "wss://relay.echoagent.dev", "room": "<房间号>", "lan": {"port": 51234, "addrs": ["192.168.1.20"]}}
```

字节串一律 base64url 无填充。

**怎么配**：

- **桌面款，插 USB 时由主机写进去**：用户在主机的设置里点「配对这台设备」，主机经串口发 `provision` 请求，带上面这些，再加上 Wi-Fi 名字和密码（用户在主机上填）。设备存进加密的闪存（ESP32 的 NVS 加密）后回 `{"ok":true}`。`unprovision` 请求清掉。
  ```jsonc
  {"id": "h1", "m": "provision", "p": {"pairing": {...}, "wifi": {"ssid": "…", "password": "…"}}}
  ```
- **穿戴款，由手机 App 用蓝牙配**：手机已经和主机配过对。手机向主机要一条新的设备配对（经它自己的加密通道），再用蓝牙写进设备。蓝牙链路要用 LE Secure Connections，配对时设备亮出（屏幕上显示或灯闪出）六位数字让人核对。
- 设备没有摄像头、不扫码。

**密钥派生**（HKDF-SHA256，ikm = `K`，salt = `echo-device/v1`，每项 32 字节）：

| info | 用途 |
|---|---|
| `relay-auth` | 设备令牌 `deviceToken`，交给中继做身份；中继只存 `sha256(base64url(deviceToken) 的 UTF-8)` 的小写十六进制 |
| `device->host` | 设备发往主机的消息密钥 |
| `host->device` | 主机发往设备的消息密钥 |

密文 `box` = base64url(`nonce(12) ‖ ciphertext ‖ tag(16)`)，ChaCha20-Poly1305，AAD 为 `<room>:<deviceId>` 的 UTF-8 字节。box 里的明文就是第 3 节的消息。

## 10. 局域网直连（草案）

设备和主机在同一个局域网时直接连主机：`ws://<地址>:<端口>/v1/device`（地址和端口在配对信息的 `lan` 里，和手机直连共用同一个端口）。

1. 设备 → 主机 `{"t":"hello","v":1,"device":<deviceId>,"n":<16 字节随机数>}`，主机回 `{"t":"hello","v":1,"n":<主机随机数>}`。
2. 两边派生这条连接的密钥：HKDF-SHA256，ikm = `K`，salt = `echo-device-lan/v1` ‖ 设备随机数 ‖ 主机随机数，info 为 `device->host`、`host->device`。
3. 设备 → 主机 `{"t":"auth","box":<用这条连接的密钥加密的 "echo-device">}`；主机认识这台设备、解得开，回 `{"t":"ready","box":<加密的 "echo-device">}`。不认识或解不开以关闭码 4001 断开。
4. 之后两个方向都是 `{"t":"send","box":…}`；心跳是纯文本 `ping` → `pong`，设备每 15 秒一次。

## 11. 经中继（草案）

中继和手机用的是同一个（`relay.echoagent.dev`），一个主机一个房间。设备不占手机的名额：

- 主机认证后把设备列表交给中继：`{"t":"devices","list":[{"id":<deviceId>,"verifier":<设备令牌的 verifier>}]}`，列表变了就再发一次整份。不在新列表里的设备立即被断开（关闭码 4003）。
- 设备连 `GET /v1/rooms/<room>`，第一帧 `{"t":"auth","role":"device","device":<deviceId>,"token":<deviceToken>,"v":1}`。
- 一个房间最多 16 台设备，和最多 4 台手机分开算。同一台设备只留一条连接，新的连上旧的断开（4000）。
- 设备发 `{"t":"send","box":…}`，主机收到 `{"t":"box","box":…,"device":<deviceId>}`；主机发 `{"t":"send","box":…,"device":<deviceId>}`。
- 设备的请求不排队：主机不在线时中继回 `{"t":"peer","online":false}`，设备显示「没连上」。按住说话、批准都是现在就要的，等主机醒来再做没有意义。

## 12. 经手机蓝牙（草案）

给没有 Wi-Fi、要省电的穿戴款。手机 App 是管道：设备和主机之间仍是端到端加密（第 9 节的 `K`），手机看不到内容。

- 一个 GATT 服务，两个特征：`rx`（手机写给设备，write without response）、`tx`（设备通知手机，notify）。UUID 待定。
- 帧：每帧第一个字节高位为 1 表示后面还有、低 7 位是序号，剩下的拼起来是一条 `{"t":"send","box":…}`。
- 语音只用 `opus`。
- 手机经它到主机的那条路（中继或局域网）转发这些 box，并告诉主机来自哪台设备。

## 13. 版本和兼容

- `hello.p.v` 是设备说的版本，回复里的 `v` 是主机决定用的版本（不超过设备的）。主机不支持时回 `version` 错误。
- 加字段、加事件、加方法不升版本：两边都必须不理不认识的字段和事件。改了已有字段的意思才升版本。
- 固件不要依赖 JSON 里字段的顺序。

## 14. 安全和隐私

- USB 直连没有加密：USB 线就是信任边界，和 USB 键盘一样。主机上任何程序都能打开这个串口，所以主机经串口只发灯的状态和（有屏幕时）短标题，不发对话内容；也只接受按键、声音和批准这几样，不能经串口派活或读文件。
- 声音只在按住键（或认出唤醒词之后）才交给主机。UAC 麦克风一直有声音，主机只在按住时录。
- 网络方式每台设备一把密钥，见第 9 节。nonce 是随机的 12 字节；同一把密钥下的消息条数远小于随机 nonce 撞车的界限。
- 中继看得到的只有：哪台设备在线、什么时候发了多大的消息。

## 15. 参考实现

- `device/sim/`：模拟设备（Python 3，只用标准库；有 libopus 时能发 Opus）。不用真硬件就能走 USB 模式：按住说话（喂 wav）、收状态、按一下批准。
- `device/firmware/esp32s3/`：ESP32-S3 参考固件骨架（ESP-IDF 5.4，USB 模式：一颗键、一颗灯、UAC 麦克风）。还没在真板子上跑过，状态见它的 README。
